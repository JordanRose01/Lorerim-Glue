## The two decisions you flagged

**Item 2 — ADOPTED as the core principle.** The glue never calls TIF fragments and never calls `SetStage`. It runs the engine's *real* dialogue session with the menu hidden ("headless session"): the engine builds the topic list, evaluates conditions with full quest/alias context, picks the INFO, plays the response, fires Begin/End fragments, handles Say Once, links, shared infos, walk-away/goodbye, service menus and story events. The glue only (1) reads the list the engine built, (2) lets the LLM choose an entry, (3) "clicks" it through the same path the menu uses. Evidence [R dialogue-engine.md]: INFO effects are Papyrus fragments fired by the engine via `TESTopicInfoEvent` begin/end; TCLT links, RNAM prompts, TWAT walk-away and response text are *not* in the runtime `TESTopicInfo` struct (the engine re-reads them from the plugin file), so any re-implementation needs an offline export and is still wrong at the edges; no published mod executes an INFO "as if clicked" without a session; the CK wiki warns fragments on `Say()` topics "are often not processed correctly". Notably CHIM's own beta "AI Quest Progression" is exactly the anti-pattern you describe: `SetStage` + hand-replicated side effects for 301 Bethesda quests, zero LoreRim mod quests [R server-quest-dialogue.md, verified pass]. It is OFF on your install (`CHIM_AI_QUEST_PROGRESSION=false`, live DB value) and must stay off while the glue drives quests; the glue will warn if it is ever on.

**Item 19 — ADOPTED, with one refinement: don't invent a third meter.** CHIM's bundled `relationship_system` plugin is *already* a separate affinity meter: −100..+100, 11 tiers, stored in `core_npc_master.extended_data->'relationships'`, read with `RelationshipManager::getPlayerRelationship($npc)` [R server-ext-patterns.md, verified pass]. Its LLM can never promote anyone into a romantic type (`rebaseRelationshipChange()` blocks it unconditionally) — only the UI, templates or a plugin calling `RelationshipManager::setRelationship()` can. Design: CHIM affinity = the general meter (read; adjust via `adjustRelationship()` when the player helps with a quest); a small glue table `glue_romance` holds what CHIM doesn't (romance stage, refusals, consent history, bribes accepted, cooldowns, last scene); vanilla rank is READ-ONLY input via `Actor.GetRelationshipRank` [V Actor.psc:284] and is never written. The side-effect list you gave for vanilla rank is [M] (not re-verified on the CK wiki this session) but the decision doesn't depend on it.

## The DLL decision (as you asked: both options, nothing installed)

OStim awareness/control needs **no** DLL (section E). Only vanilla dialogue topics might.

- **(a) DLL route.** Needs installed: Visual Studio 2022 Build Tools (MSVC v143 + Windows SDK, several GB), CMake, vcpkg, git; CommonLibSSE-NG comes through vcpkg; Address Library is already in LoreRim. Gives: topic identity by FormID, topic awareness *before* a session opens (NPCs can bring up quest matters unprompted), knowing exactly which INFO fired, hiding the menu before its first frame, main-thread stale checks, ranking by owner quest, FormIDs in the parity dump. Risks: coexisting with `SmartTalk.dll` (hooks the dialogue menu) and CHIM's click gate; struct layout on 1.6.1170 (only touch documented members).
