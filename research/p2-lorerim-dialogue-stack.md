## 0. What changes the design (read this first)

1. **Hide per element, never the whole clip, and never with `_visible`.** In CHIM's SWF the dialogue subtitle field `SubtitleText` is a CHILD of `_root.DialogueMenu_mc` (siblings: `ExitButton`, `TopicListHolder`, `SpeakerName`) [V SWF display list]. Hiding `DialogueMenu_mc` (or `_root`) also hides the NPC's real line - fatal for unvoiced (Fuz) lines. And `TopicListHolder._visible` is re-asserted by two other actors: the SWF itself (`ShowDialogueList` sets it `true` on every new list [V]) and **Improved Alternate Conversation Camera**, which, with LoreRim's `bHideDialogueMenu=1`, rewrites `TopicListHolder` visibility through `SetDisplayInfo` every frame the menu advances [V disassembly]. Use `_alpha = 0` / off-screen `_x` on `TopicListHolder`, `ExitButton`, (optionally `SpeakerName`), leave `SubtitleText` alone [I - test].
2. **IACC also rewrites `eMenuState`.** While the NPC is talking (or state is 0 = greeting) it forces `_root.DialogueMenu_mc.eMenuState = 2` each frame [V disassembly]. `eMenuState == 0` is therefore unobservable on this list; `eMenuState == 1` (TOPIC_LIST_SHOWN) remains a valid "list is ready, NPC finished" gate.
3. **A hidden menu still eats the player's input.** Any mouse-down calls `onItemSelect({mouseClick:true})` -> `onSelectionClick(true)` (global `Mouse.addListener`) [V SWF]; E/Enter = `itemPress`; Tab = `onCancelPress`; Smart Talk additionally turns every click / accept / Space press during NPC speech into an immediate `SkipText` and swallows that input frame [V source + disassembly]. The glue must make the invisible menu inert (section 3.3) or the player will pick topics / skip quest lines without seeing them.
4. **A hidden session is still a full engine session for every other mod**: player cannot move, IACC forces first person + lock-on + zoom (`bForceFirstPerson=1`, `bLockOn=1`), TDM turns the character to the speaker and blocks target lock, Considerate Followers withholds teammate lines, Follower Stats pops a HUD panel and casts a cloak, Little Lessons shifts the speech-check globals, Beneficial Speech Checks pays out on close. Sessions must be few and short; do not open/close one per utterance.
5. **IACC has per-session Papyrus switches** (`IACC.SetDisableInFirstPerson(Bool)`, `SetDisableInThirdPerson`, `SetForceFirstPerson`, `SetHideDialogueMenu` ... global natives, effective immediately) - but every setter also writes `AlternateConversationCamera.ini` [V disassembly]. Owner decision needed before the glue uses them.
6. **Session duration is set by three knobs**: Fuz Ro D-oh `WordsPerSecondSilence=2` (+1 s, cap 10 s per unvoiced response) [V], Smart Talk `[DialoguePause]` 200-800 ms added after every line via `fGameplayVoiceFilePadding` [V], and the greeting line spoken on every session open.
7. **Papyrus-only success detector for persuade / intimidate / bribe**: the winning `favordialoguescript` (from *Speechcraft Randomization*, LoreRim line 1324) does `Game.IncrementStat("Persuasions" | "Bribes" | "Intimidations")` on success [V]; an installed mod already relies on the delta across a Dialogue Menu open/close [V]. The same mod RE-ROLLS the persuasion threshold globals, and Little Lessons shifts them while a session is open - never predict an outcome, only observe it.
8. **`ObjectReference.Activate(player)` opening a dialogue session is production-proven on this list**: Immersive Interactions (line 749) and First Person Interactions (line 724) both intercept follower activation with a perk and then call `akTargetRef.Activate(akActor)` from Papyrus to open dialogue [V]. This also shows Papyrus `Activate` is not re-captured by activate perk entry points (DAK, Immersive Interactions) [I].

Cross-references to sibling reports of this round (read after mine was drafted; no contradictions found): `p2-dialogue-swf-ui.md` reaches the same SWF conclusions independently (state 3 parking, off-screen `_x` hide, IACC `eMenuState` rewrite from the original ACC source) - my contribution there is the disassembly of the INSTALLED closed-source IACC fork and of Smart Talk 1.0.5's DBVO path. `p2-chim-interplay.md` finds that CHIM's DLL calls `PauseCurrentDialogue()` + `EndDialogue()` on the addressed NPC for every player utterance, so long-lived sessions are not viable; combined with point 4 this means **one open/close per executed topic**, which makes the per-open side effects below (IACC camera snap, greeting line, Follower Stats panel/cloak, Papyrus menu listeners) the dominant UX cost of Phase 2 - the IACC decision (owner setting vs per-session toggle) should be taken before the first playtest.

### 2.1 Smart Talk (Dialogue Menu Enhancer) 1.0.5 - line 3843 - `SmartTalk.dll`

## 3. Design consequences for the hidden-session driver (Papyrus-only)

### 3.1 What to hide
Hide `_root.DialogueMenu_mc.TopicListHolder`, `.ExitButton` and (optional) `.SpeakerName` individually; keep `.SubtitleText`. Use a property that neither the SWF nor IACC writes: `_alpha` (or `_x` far off-screen for the list, which also stops mouse roll-over selection). Reasons: `ShowDialogueList` sets `TopicListHolder._visible = true` and `DoShowDialogueList` sets `ExitButton._visible` on every list [V]; IACC sets `TopicListHolder` visible/invisible per frame [V]; it does so by reading the clip's DisplayInfo and writing it back with only `visible` changed, so an alpha/position the glue set earlier is read and re-written unchanged [I - test]. The mouse cursor ("Cursor Menu", `UI.psc:10`) is a separate menu - hiding it from Papyrus is untested.

### 3.2 State reading under IACC
`eMenuState`: 1 = list shown and (under IACC) NPC silent -> safe moment to read `TopicList.entryList` / click; 2 = NPC talking or click in progress; 3 = list animating in; 0 = practically never seen while IACC's `bHideDialogueMenu=1`. Do not wait for 0.

### 3.3 Making the invisible menu inert to the player (all [I] from [V] bytecode; needs the E-tests)
- `UI.SetBool("Dialogue Menu", "_root.DialogueMenu_mc.TopicList.bDisableInput", true)` - list ignores E/Enter, wheel, roll-over, press.
- Mouse-down bypasses the list (`onMouseDown` -> `onItemSelect`), but `onItemSelect` only acts in states 1, 2, 0. Parking `eMenuState = 3` (TRANSITIONING) after the list is ready makes clicks and E no-ops; IACC does not touch state 3 when the NPC is silent. The glue's own click does not need state 1 (`onSelectionClick` fires `initMenu()` in any state; the `topicClicked` timeline sets state 2 afterwards).
- `bFadedIn = false` disables `handleInput` entirely (including Tab = leave). Decide deliberately whether Tab should remain the player's "walk away".
- Smart Talk's skip (states 0/2) stays unless the owner turns it off (2.1) - or the glue adopts "E / click = skip the NPC's line" as a documented feature.
- Never set `TopicList.bDisableSelection = true` before selecting: `doSetSelectedIndex` returns early when it is set [V].

### 3.4 Selection path facts from the winning SWF (hand-over to the SWF/CHIM-interplay report)
`TopicList.SetSelectedTopic(topicIndex)` selects by the engine's `topicIndex` (no list position arithmetic); `doSetSelectedIndex(i)` with one argument also sets `iSelectedIndex`. `onSelectionClick()` with no/false argument skips the mouse re-selection. The click completes only on `startTopicClickedTimer("off")` / `topicClicked()`. Verify completion (state -> 2, list repopulated) and never fire a second release blindly (double `TopicClicked`, 2.1).

### 3.5 Outcome detection for speech checks (Papyrus-only)
Snapshot `Game.QueryStat("Persuasions")`, `("Bribes")`, `("Intimidations")` before the click and compare after the response: the winning `MODS\Speechcraft Randomization\Scripts\Source\favordialoguescript.psc` increments them in `Persuade` (72), `ArrestPersuade` (122), `Bribe` (147, after `GetPlayer().RemoveItem(Gold, pTarget.GetBribeAmount())` at 139 and `SetBribed()` 143), `Intimidate` (165, after `SetIntimidated()` 161) [V]. The same script re-rolls `SpeechVeryEasy..SpeechVeryHard` with `RandomInt` (101-111) - thresholds on this list are not constants. (Closes most of E11 in `dialogue-engine.md`; bodies are the LoreRim-winning versions, only provider of a loose `favordialoguescript.pex`.)

### 3.6 Session hygiene
Open a session only to execute (or when the engine opens one); close it through the engine (`onCancelPress`) so Beneficial Speech Checks, Little Lessons, Follower Stats, IACC, TDM and Considerate Followers all get their close event; never leave a hidden session dangling (player frozen, teammates muted, globals shifted, target lock blocked).

### V.3 Additions - facts the report missed that change what gets built

- **A1 - `SetSelectedTopic(topicIndex)` fails OPEN to entry 0.** Bytecode @0x12aee first writes `iSelectedIndex = 0; iScrollPosition = 0` and only then searches `EntriesA[i].topicIndex`; if the index is stale (list re-populated between read and click, Say-Once topic gone, Smart Talk sort mode ever enabled) the selection silently becomes the FIRST topic and `topicClicked()` sends `EntriesA[0].topicIndex`. Build rule: after selecting, read back `_root.DialogueMenu_mc.TopicList.selectedEntry.topicIndex` (getter = `EntriesA[iSelectedIndex]`, @0xf320) and `.text`, compare with the intended entry, and abort the click on mismatch.
- **A2 - close timing vs. fragment-driven observers.** Speech-check bookkeeping (`IncrementStat`, `SetBribed`, gold removal) happens in Papyrus fragments, i.e. asynchronously after the response. Beneficial Speech Checks compares `QueryStat` in `OnMenuClose` (its handler has no menu-name test; it only registers this one menu) and Little Lessons restores the five globals on close. With the round's "one open/close per executed topic" plan, a driver that closes the session the moment the response ends can close BEFORE the fragment ran: the reward is lost, the glue's own stat delta reads 0, and Speechcraft Randomization's re-roll can land AFTER Little Lessons' `+10` restore [I]. Build rule: for speech-tagged topics poll `QueryStat` / `IsBribed()` / `IsIntimidated()` / gold for a bounded time (order of 1 s) after the response before invoking `onCancelPress`.
- **A3 - an installed mod can refuse every session.** Rite of Arcana (C2) closes the Dialogue Menu on open while its ghost state is active. The watchdog must classify "menu closed within a few hundred ms of `OnMenuOpen`, no topic executed" as REFUSED (tell the LLM the NPC cannot be talked to now) and must not retry in a loop. The same script and `[LoreRim] Respec` prove `UI.InvokeString("HUD Menu", "_global.skse.CloseMenu", "Dialogue Menu")`, and `[LoreRim] TM` proves `PO3_SKSEFunctions.HideMenu("Dialogue Menu")` (`PO3_SKSEFunctions.psc:1108`; implementation re-opened: `UIMsgQueue->AddMessage(a_menuName, RE::UI_MESSAGE_TYPE::kHide, nullptr)`, powerof3/PapyrusExtenderSSE `src/Papyrus/Functions/UI.cpp`) as Papyrus-only FORCE-CLOSE primitives for the watchdog when `onCancelPress` does nothing (in state 0 it only calls `SkipText`). Whether a forced kHide leaves MenuTopicManager clean is [I] - last resort only.
- **A4 - `Game.GetDialogueTarget()` is production-proven on this list** (`LittleLessonsVirtueThiefEffect.psc:31`, SKSE `Game.psc:446`). For engine-opened sessions (ForceGreet, guards, couriers) the handler should take the speaker from it, not from the crosshair (BTPS substitutes the pick, 2.10) and not by Follower Stats' cloak trick.
- **A5 - IACC zoom scales with distance.** The original `main.cpp` computes the dialogue FOV from `atanf(prefDist / distance)`. A session opened by Papyrus `Activate` on an NPC several metres away (normal for CHIM voice chat) gives a much stronger zoom-in than an E-press at arm's length, on top of the first-person snap [I for the closed fork; formula V for the original]. Build rule: only open a hidden session inside normal talk range (or take the decision to the owner together with the IACC knobs); IACC also stays inert on a mount, carriage, in beast form and in non-1st/3rd camera states - the driver must not wait for a camera change as a "session started" signal.
- **A6 - IACC rewrites ALL DisplayInfo fields every frame, from a read taken in the same call.** Verified: flags word zeroed, GetDisplayInfo, optional `|= 0x40`, SetDisplayInfo - even in states 2 / 3 where it changes nothing. Read and write happen inside one UI-thread call, so a Papyrus `_alpha` / `_x` write (queued UI task) cannot be interleaved and is carried forward - this upgrades the report's 3.1 inference from "plausible" to "follows from the code"; an in-game check is still needed for the FIRST frames (before the glue's `OnMenuOpen` handler has run).
