## 1. CRITICAL - the SFF integration is dead: three wrong EditorIDs

`LRG_Followers.psc` reads SFF's globals by editor id:

```
55:  return PO3_SKSEFunctions.GetFormFromEditorID("SFFCanRecruitMore") as GlobalVariable
59:  return PO3_SKSEFunctions.GetFormFromEditorID("SFFCurrentFollowerCount") as GlobalVariable
```

The globals in the installed `Simple Follower Framework.esp` are:

```
GLOB 05000001  SFF_CanRecruitMore
GLOB 05000002  SFF_CurrentFollowerCount
GLOB 05000805  SFF_FollowerSandbox
```

**With underscores.** A scan of every `.esp/.esm/.esl` in the load order (3,696 files, 1.3 GB) finds no
form whose EditorID is `SFFCanRecruitMore`. The literal string occurs in exactly two plugins - SFF's own
esp and `LoreRim - xEdit64 Output\Simple Follower Framework Patch.esp` - and in both it is a **Papyrus
property name inside the quest's VMAD**, not an EDID. `GetFormFromEditorID` matches the EDID, so both
lookups return `None`.

That single miss decides everything downstream, because `SffPresent()` *is* the `SFFCanRecruitMore`
lookup (line 62-66):

* `SffPresent()` is **always false** in this modlist.
* `IsSff()` is always false -> `fw` is never `sff`. A real SFF follower reports `fw:custom`.
* `FolState()` never emits `slot:`, `cap:` or `prim:`. The server's `hide_when_cap_full` rule
  (`lrg_core.php:1472`), the "He has N of M companions" line and the "cannot take anyone else" line in
  `<companion_status>` are **dead controls** - they can never fire from a real game.
* **`RepairGhost(actor, 0)` can never promote.** Line 231 is `if aiMode == 0 && SffPresent()`, so mode 0
  - the shipped default, and the mode the owner notes tell him to leave alone ("Make her real if there
  is room") - falls straight through to the undo path on every ghost, every time.

Nothing offline could catch this: `test_gates` proves the *server* rule by injecting a synthetic
`fol=...,cap:0` string (and it passes), and there is no Papyrus test harness. The same three lines are
also wrong in `PROTOCOL.md` 10.19 and in the investigation `pt9-followers.md`, which is where the
spelling came from.

**Smallest fix** - `LRG_Followers.psc` lines 55 and 59:

```
"SFFCanRecruitMore"        -> "SFF_CanRecruitMore"
"SFFCurrentFollowerCount"  -> "SFF_CurrentFollowerCount"
```
then recompile and reinstall, and correct the two names in `PROTOCOL.md` 10.19. See finding 4 before
trusting the `cap` value that then starts arriving.

## 2. CRITICAL - the undo path permanently destroys the NPC's own recruit dialogue

`RepairGhost()`'s undo (lines 246-259):

```
Faction cf = FacCurrentFollower()
if cf
    akNpc.RemoveFromFaction(cf)
endif
Faction pf = FacPotentialFollower()
if pf
    akNpc.RemoveFromFaction(pf)          ; <-- this line
endif
```

`PotentialFollowerFaction` (`0005C84D`) is a **base-record faction of every recruitable NPC in Skyrim**
(checked: Ria and Vilkas both carry `SNAM 0005C84D rank 0` in `Skyrim.esm`), and it is what the vanilla
recruit line is conditioned on. The CTDA list of `DialogueFavorGenericFollowBranchTopic`, "Follow me. I
need your help.", winning plugin `Skyrim.esm` (INFO `0D8DE0`, and its sibling `05C829`):

```
GetInFaction  PotentialHireling(000BCC9A)         == 0
GetIsVoiceType VoicesFollowerNeutral(000D23AC)    == 1
GetGlobalValue PlayerFollowerCount(000BCC98)      == 0
GetInFaction  CurrentFollowerFaction(0005C84E)    == 0
GetInFaction  PotentialFollowerFaction(0005C84D)  == 1     <-- membership
GetRelationshipRank                                >= 1
```

`RemoveFromFaction` on an actor persists in the save. After one undo, **that NPC can never be recruited
through her own dialogue again** - not by the player, not by the follower verbs this very round added,
not after a reload. She is also silently unrecoverable without console work.

The undo goes **strictly further than the edit it claims to undo**. CHIM's
`AIAgentNpcUtil.MakeFollower` (`AIAgentNpcUtil.psc:381-386`) only *adds*:

```
akTarget.AddToFaction(PotentialFollowerFaction)
akTarget.SetFactionRank(PotentialFollowerFaction, 0)   ; 0 is the base rank anyway
akTarget.AddToFaction(CurrentFollowerFaction)
akTarget.SetFactionRank(CurrentFollowerFaction, 1)
```

so for anyone who was already a potential follower, CHIM changed nothing about `PotentialFollowerFaction`
and the glue removes it.

Finding 1 makes this near-certain rather than occasional: with `SffPresent()` false the undo is the
**only** outcome of the default repair mode. The exact P-F2 scenario the round wrote for itself
(`MakeFollower` a second NPC while Lydia is recruited) ends in Lydia's replacement being made
permanently unrecruitable.

**Smallest fix** - delete the `pf` block (lines 252-255). Removing `CurrentFollowerFaction` alone fully
clears the ghost: `IsGhost()`, CHIM's own `isInFaction(VanillaCurrentFollowerFaction)` checks and SFF's
`GetDialogueFollowerTarget()` all key off `CurrentFollowerFaction`, and membership of
`PotentialFollowerFaction` by itself makes nobody a follower. If CHIM's rank write must be reverted at
all, use `SetFactionRank(pf, 0)` (a no-op on the base value) - never `RemoveFromFaction`.

## 3. MAJOR - the "dismissed follower" exclusion never runs (wrong EditorID again)

```
41:  return PO3_SKSEFunctions.GetFormFromEditorID("DismissedFollower") as Faction
```

The vanilla faction's EditorID is **`DismissedFollowerFaction`** (`Skyrim.esm 0005C84C`). No form in the
load order has EditorID `DismissedFollower` (scanned: 0 of 3,696 plugins contain the token
`DismissedFollower\0`). `FacDismissed()` therefore always returns `None`, and `IsGhost()`'s test

```
Faction dis = FacDismissed()
if dis && akNpc.IsInFaction(dis)
    return false
endif
```

is unreachable. The file's own comment says these are "what keeps a dismissed custom follower out of the
repair" - one of the two guards (the other is Inigo's `WaitingForPlayer == -1`) does not exist. Any NPC a
mod dismisses by clearing the teammate flag and adding `DismissedFollowerFaction` while leaving
`CurrentFollowerFaction` set is classified as a CHIM ghost and repaired - i.e. her factions stripped
(finding 2) and CHIM's follow package applied to somebody who was just sent home.

SFF itself is safe by luck, not by this guard: `CleanupDismissedFollowerActor` does not remove
`CurrentFollowerFaction`, but SFF's `Clear()` of the alias does (every alias in the quest carries
`ALFC 0005C84E`). The 25+ custom-follower mods in this list each have their own dismissal.

**Smallest fix** - `"DismissedFollower"` -> `"DismissedFollowerFaction"` (or
`Game.GetForm(0x0005C84C) as Faction`, matching the two factions either side of it).

## 4. MAJOR - `cap` is not "the number the real recruit entry is conditioned on"

Claimed in the build report (3.1), in `PROTOCOL.md` 10.19, in the MCM help and in `lrg_core.php:1447`.
The real vanilla recruit INFO is gated on `PlayerFollowerCount == 0` (see the CTDA dump above), and SFF
sets that global itself:

```
SFF_UpdateFollowerGlobals:   PlayerFollowerCount = (iSFFFollowerCount > 0) ? 1 : 0
                             SFF_CanRecruitMore  = (iSFFFollowerCount < SFF_GetMaxFollowersSafe())
```

The two disagree for every follower after the first: with 1 of 4 slots used, `SFF_CanRecruitMore` is 1
while the real entry has already stopped being offered. Today this is invisible because `cap` is never
sent (finding 1); the moment finding 1 is fixed, `hide_when_cap_full` becomes **less** strict than the
entry it is supposed to mirror, and `<companion_status>` will tell the model the player can take someone
else when the game will not offer it.

**Smallest fix** - either drop the `hide_when_cap_full` claim to what it really is ("the framework says
there is no free slot"), or send `PlayerFollowerCount` alongside `cap` and hide on that. No code change
is urgent while finding 1 stands.

## 5. What held up

* **`IsGhost()` is otherwise correct.** A waiting SFF follower keeps the teammate flag
  (`FollowerWait` only writes `WaitingForPlayer = 1`), so she is never a ghost; an SFF animal is a
  teammate too (`SetAnimal` -> `SetPlayerTeammate(1,0)`); a dismissed SFF follower loses
  `CurrentFollowerFaction` with the alias. Inigo's `-1` convention is honoured and the glue never writes
  `WaitingForPlayer` anywhere.
* **The repair never runs on a non-ghost.** `IsGhost` is re-tested in `RepairFollower` (line 1609) and
  again at the top of `RepairGhost`; the guard list in front of it (feature on, not dry run,
  `bFollowerRepair`, no scene, no dialogue session, no menu, not in combat, loaded, alive) is complete,
  and it is queued onto the quest's own tick, never run inline from a speech event.
* **It cannot double-fire with CHIM's shortcuts.** `lrgFollowerPolicy()` is the last filter of all, at
  brace depth 0 in `functions.php`, and only ever removes; the `follower` service kind has its own
  narrower hide condition (`$menuless && fv && the turn really has follower verbs`) and its own
  `hide_follower` list; the verb arbiter returns "execute nothing" on ambiguity, on a negated order and
  when she has no entry, and never substitutes CHIM's shortcut for a recruit the engine is not showing.
* **The intimacy invite does not recruit.** `ExtCmdLRG_Invite` is recorded and removed server-side and
  never reaches the game; no glue script outside `LRG_Followers.psc` writes a faction, a teammate flag
  or a follower alias (grepped all 10 `.psc`).
* **The conversation hold still skips teammates unconditionally** - `LRG_Main.psc:1179`
  `if akNpc.IsPlayerTeammate()` is before, and independent of, the `bFollowerHoldSkip` line at 1182, so
  a missing ini key (which reads FALSE) cannot start freezing real followers.
* **MCM wiring is complete.** All five new keys have a `settings.ini` default and a reader
  (`test_mcm_wiring`: `fol` and `fv` as wire keys written-by-a-`.psc` and read-by-a-`.php`;
  `bFollowerHoldSkip` / `bFollowerRepair` / `iFollowerRepairMode` read by `LRG_Main.psc`).
* **Wire compatibility is additive both ways.** `fol=`'s value carries no `;` or `=`, so an old server
  parses it as one opaque value; the server reads absent `fol` / `witchim` as "say nothing" and applies
  the freshness rail. `witchim` can only make the privacy gate stricter, and a ghost is still counted in
  `wit` as well.
* Nothing in the menuless driver, the weapons prep, say-first or the outro hold was touched by this lane.
